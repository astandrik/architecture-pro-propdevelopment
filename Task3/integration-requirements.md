# Требования к внешним интеграциям: Smart Home

## Контекст

PropDevelopment внедряет два сервиса от партнёра через платформу «Умный дом»:

1. Интеллектуальный домофон: видеодомофон + распознавание лиц (биометрия) + автоматическое открытие двери
2. Интеллектуальный шлагбаум: распознавание номеров автомобилей + автоматический доступ

Сервисы доступны через мобильное приложение собственников. Интеграцию обеспечивает новый stateless-адаптер `smart-home-gateway` в домене ЖКУ. Привязки устройств к ЖК/квартирам и аудит-лог хранятся в существующей `tenant-core-db`.

---

## A. Требования к безопасности

### Биометрические данные

- Биометрия (шаблоны лиц), спецкатегория ПДн по 152-ФЗ ст. 11
- Биометрические данные **не хранятся** в системах PropDevelopment. Обработка и хранение на стороне партнёра
- Договор поручения обработки ПДн с партнёром по 152-ФЗ ст. 6 ч. 3
- Письменное согласие собственника на обработку биометрии. Отзыв согласия = удаление шаблонов у партнёра

### Данные автомобильных номеров

- Номера авто, персональные данные
- Хешированные привязки «номер → разрешение доступа» хранятся на стороне партнёра, без сырых номеров в системах PropDevelopment
- Распознавание и сопоставление выполняется партнёрской платформой

### Минимизация данных

- `smart-home-gateway` получает от партнёра только решения (разрешён / запрещён доступ), без сырых изображений и биометрических шаблонов
- Между PropDevelopment и партнёром передаются: идентификаторы устройств, команды управления, события доступа

### Шифрование и сетевая изоляция

- TLS 1.3 на всех каналах между системами
- `smart-home-gateway` в выделенном сетевом сегменте, доступен только из `tenant-core-app`
- Rate limiting и валидация входных данных на gateway

### Аудит

- Все события доступа (открытие двери/шлагбаума, отказ) логируются в `tenant-core-db`: кто, когда, какое устройство, результат
- Данные аудита передаются в хранилище данных через существующий CDC-канал `tenant-core-db`

### Инциденты

- Компрометация IoT-устройства: отключение через API партнёра, оповещение собственников, фиксация инцидента
- Компрометация API key: партнёр отзывает ключ, выдаёт новый. Запросы со старым ключом блокируются

## B. Протоколы аутентификации и авторизации

### Аутентификация собственников

| Участок | Протокол | Детали |
|---|---|---|
| Собственник → мобильное приложение | OAuth 2.0 / OIDC | Через существующий auth-service-1 (Keycloak) |
| Биометрия на домофоне | Распознавание лица (фактор «что ты собой представляешь») | Аутентификация на стороне партнёра, результат передаётся в gateway |

### Аутентификация между системами

| Участок | Протокол | Детали |
|---|---|---|
| Мобильное приложение → tenant-core-app → smart-home-gateway | JWT | Каждый сервис проверяет, что токен выписан для него (поле audience). Токен передаётся в заголовке Authorization, не в URL |
| smart-home-gateway → Smart Home Platform | mTLS + API key | Клиентский сертификат (certificate pinning). API key единый на организацию (не на пользователя), хранится в vault, ротация по расписанию |
| Smart Home Platform → IoT-устройства | Управляется партнёром | Требования фиксируются в договоре |

### Авторизация

- RBAC: роли — собственник, менеджер УК, администратор
- ABAC: атрибуты — идентификатор ЖК, номер квартиры, время суток, для доступа к конкретным устройствам
- Собственник управляет только устройствами своего ЖК и квартиры
- MFA обязательна для критических операций: регистрация биометрии, изменение списков доступа, добавление/удаление доверенных лиц и автомобилей

### Временный доступ (JIT)

- Временные гостевые пропуска (курьер, гость) с автоотзывом по истечении срока
- Собственник задаёт срок действия и тип доступа (только домофон / только шлагбаум / оба)

## C. Взаимодействие между системами

### Внутренние вызовы (PropDevelopment)

| Источник | Назначение | Протокол | Описание |
|---|---|---|---|
| Мобильное приложение | tenant-core-app | REST, WS | Существующий канал |
| tenant-core-app | smart-home-gateway | REST | Управление устройствами. tenant-core-app хранит списки доступа и аудит-лог в tenant-core-db |

### Внешние вызовы (PropDevelopment ↔ партнёр)

| Источник | Назначение | Протокол | Описание |
|---|---|---|---|
| smart-home-gateway | Smart Home Platform | REST / mTLS | Команды управления (добавить/удалить шаблон, открыть дверь). API партнёра не предоставляет операций чтения и перебора шаблонов |
| Smart Home Platform | smart-home-gateway | Webhook / HTTPS | Push-уведомления о событиях (дверь открыта, доступ отклонён) |

### Паттерны надёжности

- Idempotency keys: каждый мутирующий запрос к партнёру (добавить шаблон, удалить доступ, открыть дверь) содержит уникальный ключ. Если запрос уходит повторно из-за таймаута или сетевого сбоя, партнёр выполнит его только один раз. Без этого повторный запрос «открой дверь» откроет дверь дважды или создаст дубль шаблона.
- Circuit breaker: если API партнёра не отвечает или возвращает ошибки N раз подряд, gateway перестаёт отправлять запросы на заданный интервал. Пользователь получает сообщение «сервис временно недоступен» вместо зависания. Когда партнёр восстанавливается, gateway возобновляет работу.
